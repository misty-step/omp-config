# Information Architecture — the taste

What separates world-class docs from autogenerated prose. This skill supplies judgment a model will not derive alone. Encode it, then let the repo's shape choose details.

## Diátaxis is the spine

Four modes, different jobs, never blended on one page:

| Mode | Answers | For |
|---|---|---|
| Explanation | "why is it built this way?" | understanding — architecture, decisions, trade-offs, *lore* |
| Reference | "what exactly is X?" | lookup — APIs, schemas, config, CLI, exports |
| How-to | "how do I accomplish Y?" | a goal — add a feature, debug a flow, run locally |
| Tutorial | "teach me from zero" | a newcomer's first guided pass |

Most codebases lack **Explanation** (the *why*). They contain too much autogenerated **Reference** (the *what*, which code already states). Give more weight to intent, flow, and decisions. This context lives only in maintainers' heads and git history.

## Page taxonomy — types, not a fixed tree

Use page types, then let recon choose which types exist and how they nest. A small library needs five pages. A monorepo needs a section per service.

- **Overview / architecture** — the system's main structure: major components, how they compose, and how data and control flow. A useful diagram can replace three paragraphs.
- **Entry points** — where execution starts (main, handlers, CLI, jobs, cron).
- **Systems / modules** — one page per load-bearing subsystem; state what it owns, its boundary, and who calls it.
- **Data model** — schemas, key entities, persistence, migrations.
- **Interfaces** — public APIs, events, CLI surface, config/feature flags.
- **Build / test / deploy** — how to run it, prove it, and ship it.
- **Conventions** — the patterns a contributor must match (the non-inferable ones; skip what the code obviously shows).
- **Decisions / lore** — *why* the non-obvious choices were made; pull them from git history, ADRs, and code comments. These pages are often the most useful and least available.
- **Glossary / maintainers** — domain terms; who owns what.

## Diagrams that earn their place

A diagram must answer a question more clearly than prose. Use Mermaid by default (renders everywhere, diffs as text, parseable by the render oracle).

- **Architecture / container** — component composition (C4-ish). One per repo.
- **Sequence** — for the 2–4 flows that matter (request lifecycle, auth, the
  core job). Trace from ingress to persistence.
- **Data-flow / dependency** — module graph or data movement when coupling is
  the thing to understand.
- **State machine** — only for genuine state (orders, jobs, sessions).

Do not use decorative diagrams. Do not use a diagram that only repeats a list. Ground every node and edge in source that the accuracy oracle can verify.

## What a world-class page looks like

- **Lead with the job-to-be-done**, not a definition dump.
- **Link to source lines** (`path:line`) so a reader can reach ground truth and the accuracy oracle has a checkable source.
- **Capture intent and flow.** Do not paraphrase function bodies. Restated code adds drift risk without understanding.
- **Use one diagram at most** unless a second answers a distinct question.
- **Cross-link** to the pages a reader needs next. The navigability oracle exercises these links.
- **State the why** for non-obvious choices, with a source (commit, ADR, comment). Unsourced rationale is a guess.

## Adapt to the system shape

- **CLI** — list commands and flags as reference. Add one how-to per common task. Add a flow diagram of arg → action → output.
- **Service/API** — show the request lifecycle sequence, endpoint reference, data model, and deployment topology.
- **Library/SDK** — provide public API reference, integration how-tos, a consumer-build quickstart, and minimal internals unless contributors need them.
- **Monorepo** — map the top level, then add a section per package or service. Do not use one giant page.
